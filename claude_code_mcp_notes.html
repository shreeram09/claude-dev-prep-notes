Claude Code, MCP & Integration

Module 3 · make it configurable, shareable & safe — beyond your machine

Theme: it works on my machine ✔ → for teammates / prod / auditors each convenience becomes a failure: wrong mode, buried rule, local path, committed key, staging-only OAuth.

1 · Permission modes & human gates

Claude Code runs the same agent loop (Module 2) + a permission layer. Flow: explore → plan → code.

Plan mode = good default for unfamiliar / high-stakes code.
  • acceptEdits: scoped to inside working dir; protected paths + other shell cmds still prompt.
  • auto (research preview): blocks prod deploys, mass deletes, cred exfil, force-push main. Reduces prompts ≠ guarantees safety.
  • Want fewer prompts safely? use auto, never bypass on a workstation.
bypass also skips the protected-path guard!

Where settings live (higher = harder to override)

Deny always beats allow, in every mode (even bypass). Enterprise deny = most durable governance.

Rules stack on the mode: mode = default for session, rules = exceptions.

Where the human gate goes: “worst case if unchecked?”

No gate
low-cost, reversible: formatting, in-dir edits (acceptEdits)
Gate
hard to undo / sensitive path / outside dir / destructive shell → deny rule or default/plan
Human must merge
code marked sensitive: agent = input, never the only gate
Postmortem: bypass for “just renaming endpoints”; pattern /v1/legacy/ also matched /deploy/config/prod/; cleanup.sh deleted prod configs with zero prompts. Set deny on sensitive dirs BEFORE changing mode. Checkpoint 1 recipe: acceptEdits + deny Bash(rm:*), Bash(git push:*), Read(.env.production).

2 · Durable project context

Permissions = what the agent may do. This section = what it knows & how it behaves next session.

CLAUDE.md — loaded every session

  • /init makes a starter file → validate & trim.
  • Keep ONLY behaviour-changing rules: test cmds, conventions, off-limits paths.
  • Bigger file = each rule weighs less. 847-line file → agent edited /legacy/tokens/ despite line 347 saying don't. History/archives → separate docs or Skills.
  • The rule you can't afford to lose → a hook.
Past a few hundred lines? audit & move out.

Rules files — .claude/rules/

Path-scoped guidance via YAML paths: glob (e.g. src/db/**/*.sql) → loads only when matching files are touched.

No paths field = loads at launch like CLAUDE.md (subfolders are just organisation).

Universal → CLAUDE.md. Local to one area → rules file.

Hooks — your script at a lifecycle event (fires EVERY time)

CLAUDE.md “run Prettier” = followed most of the time. Hook = every time, any mode. Guardrail vs convention. Checkpoint 2: PreToolUse, matcher Read, script exits 2 on .env.production.

Subagents — isolated context, return only a summary

  • Start clean: no main history, no accumulated files.
  • Built-in Explore & Plan SKIP CLAUDE.md + git status (speed) → your project rules aren't there. Need the rules? use general-purpose or a custom subagent.
  • Custom subagent (.claude/agents) doesn't see skills → list them in its frontmatter. Built-ins have no preloaded skills.
  • Best for exploration & parallelisable work.
Rule ignored by a subagent? check what it actually loaded.

Which mechanism carries which knowledge?

CLAUDE.md – always; persistent cost, dilutes. Universal constraints.
Rules file – path-triggered (if scoped). Narrow guidance.
Hook – at event; ~0 context. Enforced guardrails, audit.
Subagent – delegated; summary only. Exploration, parallel work.
Handles well: projects revisited across many sessions. Skip for one-off tasks – setup overhead isn't worth it.

3 · Packaging workflows: skills, commands, plugins

Goal: teammate gets your setup in one install, not a page of manual steps.

Skill = SKILL.md (front matter + steps), author once…

…but each runtime loads & sandboxes it differently:

Claude Code
found in .claude/skills; loads on description match or /name; runs in your terminal under mode + deny rules.
Messages API
sent with request; runs in code-exec container, NOT your machine. Needs code-execution + skills beta headers.
Agent SDK
runs in your process; skills load ONLY if settingSources set explicitly (else skill silently does nothing).
Managed Agents
skill listed on the agent resource; Anthropic sandbox; beta header managed-agents-2026-04-01; no ZDR/HIPAA.

3 portability rules

  • Description = matching criterion – vague one fails everywhere.
  • No local-filesystem/tool assumptions in the body (breaks in container). Or document them.
  • Subagents don't inherit skills – list explicitly.
“Runs everywhere” is designed for, not automatic.

Explicit entry points

  • Skills are now the recommended format for BOTH auto & explicit use: /skill-name. disable-model-invocation: true = manual-only workflow. .claude/commands/ = legacy.
  • Plugin commands are namespaced: plugin payments + run-tests → /payments:run-tests. Rename plugin = rename every command.

Plugin = versioned bundle, shared via marketplace

  • Skill – on-demand procedure · Command – explicit trigger · Plugin – share/version across team.
  • Risk: a guardrail (deny rule/hook) you relied on locally is NOT in the bundle unless you list it.
  • Managed-scope plugins outrank user/project settings.
Cost: pay setup once (plugin) vs every dev by hand.
Postmortem – “installed ✔, failed for everyone”: SKILL.md ran /Users/alexmorgan/projects/deploy-utils/validate.sh (absolute path) + silently needed DEPLOY_TOKEN from author's shell → 3 people, 2 hours. Install copies files; execution resolves paths.
Fix: $CLAUDE_PROJECT_DIR/scripts/validate.sh (project scripts) · ${CLAUDE_PLUGIN_ROOT} (bundled scripts) · bundle every dependency · document + validate env vars at install · test on a clean machine.

4 · Building & configuring MCP servers

MCP server = a process that exposes capabilities; build once, every MCP client reuses it (Claude Code has a built-in client).

Tools
actions the model calls
Resources
read-only data fetched by address into context (direct = fixed URI, templated = has parameter). Client support varies.
Prompts
vetted instruction templates invoked by name; maintained in one place.

Transport = where the server runs

Context cost: each server adds tool defs. Claude Code defers them & searches for tools on demand (opt-in: load upfront if <≈10% of window). Connect only what you need.

Config scope = who loads it

Local – ~/.claude.json under this project; only you, one project.
User – your personal settings; all your projects; not shared.
Project – .mcp.json in repo root; teammates get it on clone. stdio ⇒ each machine needs the runtime (e.g. Node).
Enterprise – admin-managed; pushed to all; locked.
  • Per-tool rules: mcp__server__tool – allow mcp__github__create_issue, deny a write tool; deny beats allow.
  • permission rule = may it RUN (governance) · enabled flag (API mcp_toolset) = does model SEE it (context/scope).
  • stdio can't be “shared” via .mcp.json → looks shareable, isn't a remote service.
Transport ⟂ scope, but pick transport first.

GitHub vs Linear — same transport, different auth

GitHub MCP (remote HTTP): Personal Access Token as Bearer header, via env var reference — service credential you store.
Linear MCP (remote HTTP): OAuth – 401 → browser sign-in → token issued & stored; nothing copied by hand.
Leaked key: inline Bearer sk-abc123… in committed .mcp.json → in history, 3 teammates, CI runner. Overwriting ≠ removal → must ROTATE (broke 2 other services, 3 hrs). Use Bearer ${WAREHOUSE_MCP_TOKEN}. Backstop: CLAUDE.md rule + PreToolUse hook (exit 2) on .mcp.json writes with credential patterns.

Prompt caching & RAG (context-cost cousins)

  • Caching: cache_control: ephemeral on last block to cache (≤4); order tools→system→messages; exact-match prefix; TTL 5 min (reset on read) or ttl: 1h; min ≈1,024 tokens.
  • Classical RAG: chunk → embed → index upfront, similarity match later. Agentic search: no index; model fetches live (like deferred MCP tool loading).
  • RAG scales flat but is only as good as what it finds → descriptive file names, grouping.
Retrieval misses ⇒ model never sees it.

5 · Enterprise integration & auth

Prototype asks “does it connect?” Production asks: who is it acting as · what data · where does it go · can admin lock it · is it logged?

Secrets: 3 practices

  • Separate: config holds a variable reference, value lives elsewhere (config gets committed/cloned).
  • Store: env var injected at runtime for local/short-lived (CI secret); secret store if shared/auditable (one rotation updates all, logs who read).
  • Rotate: on schedule + immediately after exposure; leaked ≠ re-secret-able. Works cleanly only if 1 & 2 held.
  • Narrowest scope per credential · record which services use which key.
Trace fix: rotate rejected key → inject as env var in CI → config references the var (Fix B).

Cheat-sheet: 7 takeaways

① mode = risk decision, not speed; deny rules first · ② AI review = findings to triage; verify runtime claims; human gates on irreversible actions · ③ skills portable only by design (headers / settingSources / sandbox) · ④ right mechanism per concern: CLAUDE.md, rules, hooks, subagents · ⑤ plugins need relative paths, documented env vars, clean-machine test · ⑥ transport (where it runs) + scope (who loads it) must match · ⑦ enterprise: OAuth / env-var keys, audit hooks, managed config — before the security review.
