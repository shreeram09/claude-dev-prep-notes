Production-Grade Prompting, Agents & Tool-use

Module 2 · turning a Claude prototype into a system that survives production

Core idea: dev works on small inputs, short sessions. Prod has big tool outputs, long sessions, dropped streams, irreversible actions. Each topic = one hidden failure mode.

1 · Prompting craft

Don't just add words. Diagnose the failure type → add the ONE missing technique.

XML tags = separate instructions from data (<ticket>, <sample_input>). Few-shot = show, don't tell.

Re-prompted 3× and still broken? STOP adding text — diagnose!
Long prompt → long, slow output (6-pass trace: no accuracy gain)
Classifier fix: “Classify into exactly one of: BILLING, TECHNICAL, ESCALATION. Return only the label. No other text.” + 2 few-shot pairs → parser-safe output every time.

Structured outputs (move control INTO the API)

  • JSON outputs – output_config.format = json_schema → constrained decoding, valid JSON every time.
  • Strict tool use – strict: true → tool args validated against schema.
  • Costs: 1st call slower (grammar compile, cached 24h) · extra input tokens · still check stop_reason (refusal, max_tokens = bad output) · ✗ can't combine with prefill.
schema ≠ guaranteed success!
always check stop_reason

2 · Extended thinking

Model reasons first (a thinking block precedes the answer). Adaptive on current models → tune with effort, not old budget_tokens (deprecated → 400 error). Thinking tokens cost like output tokens.

ON ✔

3 · Tool use & schema design

Claude never runs tools. It asks; your code executes & returns the result. Most bugs live at this boundary.

Every tool_use needs a tool_result with the SAME id in the very next user turn — or 400 error.

4 block types

  • text – keep it in history when it sits beside a tool_use (don't drop!)
  • tool_use – name + unique id + input (assistant)
  • tool_result – matching id, content, optional is_error (sent as user role; all results for a turn go in ONE message)
  • thinking – return unchanged (see carry-back)
Checkpoint 3: result had toolu_02 but call was toolu_01 → fix the ID.

Schema anatomy = name + description + input_schema

Description is what Claude routes on. Write 3–4 sentences: what it does · when to use · when NOT to use · what it returns.
✘ “Use this to find information.”   ✔ “…current balance for an account ID. Do NOT use for transaction history.”
  • required only if the call is meaningless without it (else Claude fabricates values)
  • optional for sensible defaults / absence is meaningful
  • dependent calls → separate turns · independent → parallel tool_use blocks (disable_parallel_tool_use to force one)
  • Overlapping params → name the domain/trigger in each description. Can't separate? merge into one tool w/ a type param.
  • Over-tooling degrades routing → start with the minimum set.
search_docs vs get_context_summary: both said “find info” → add an exclusion sentence to BOTH.

MCP – use someone else's tools

  • Loop is unchanged; only who wrote the schemas changes.
  • Every connected server's tool defs eat context even when unused → enabled / defer_loading in mcp_toolset (needs beta header mcp-client-2025-11-20).
  • Transports: stdio (local subprocess) · Streamable HTTP (remote; SSE-only deprecated). API connector = remote HTTP only.
  • Use MCP if maintained server exists · manual for description quality · both: allowlist + tune descriptions.
Narrow the tool set AND sharpen descriptions — two separate levers.

4 · Streaming

API sends events; you assemble the blocks. Final message = same as non-streamed.

“Read loop ended” ≠ “message complete”. Track a stop_seen flag.
Use streaming for user-facing long output. Skip for short / backend jobs (no partial-state risk).

5 · Context engineering

Window = fixed budget: system + history + tool defs + every tool result + output. Too big → API error / model_context_window_exceeded; nothing is silently truncated, you must manage it.

Model pick: start Sonnet → Opus only if evals say so → Haiku only if quality loss is acceptable (measured!).

Measure tokens on your LARGEST real input, not fixtures.

4 strategies

Prune – rewind to earlier msg, drop dead-end path. Lose: what was learned after.
Compact – summarise history (/compact; API server-side compaction beta). Lose: un-summarised detail.
Clear – new session, empty context, for unrelated task. Lose: all (persist in CLAUDE.md/storage).
Subagent – isolated window, scoped task, returns short summary. Lose: its reasoning trail.
  • Summarizer prompt matters: “summarise” ✘ vs “keep file paths changed, decisions, errors + fixes” ✔
  • Prompt caching – cache_control: ephemeral on stable prefix (system, tools, docs), ≤4 breakpoints → cheaper turns.
  • count_tokens – measure before sending; gate oversize requests.
  • RAG breaks at: chunking (size + overlap) · embedding match (misses exact IDs → add lexical) · prompt assembly.
Subagents start clean: no history, no skills (permissions DO carry over).

6 · Building a production agent

Agent = multi-step tool loop + managed context + a goal. Choose the simplest pattern that works – move up only when it can't cope.

Workflow: error cost high, step guardrails, standard observability.
Agent: needs transcript-level tooling.

3 wiring paths – who runs the loop?

Raw Messages API
You own EVERYTHING: loop, tools, context, retries, exit.
Max control, max upkeep.
Agent SDK
Loop runs in YOUR process; you execute tools.
set settingSources explicitly (CLAUDE.md/skills).
Managed Agents (beta)
Anthropic runs loop + sandbox; you stream events. Long runs. Beta header managed-agents-2026-04-01.
Deal-breaker: Managed Agent sessions are stored server-side → not eligible for ZDR or HIPAA BAA. PHI/ZDR → Agent SDK or raw loop on a covered config. Constraint picks the path, not convenience.

The loop — 4 steps (any path)

Exit must not rely on Claude “volunteering” to stop.

HITL — ask: “worst outcome if this step runs unchecked?”

Before destructive call
write / delete / send. HIGH – irreversible.
After planning step
wrong plan = wrong result. MEDIUM
On unexpected output
error flag, empty, out-of-bounds. VARIES
Postmortem: config-agent edited a customer rate-limit; validate_config passed (value in range) → app throttled. Validation checked the file, not downstream dependants. Fix: gate between “change proposed” and “write committed”. 
if block.name == "update_record" and not request_human_approval(block.input):
    result = "Update cancelled by reviewer."
else:
    result = execute_tool(block.name, block.input)

Regulated data → decides endpoint + creds first

Privilege: approved gateway, SSO, app-layer logging.

7 · Agent memory & Skills

Decide memory scope at DESIGN time — refactoring under prod pressure costs far more.

Dev = 1 long session. Prod = many short ones with piling state (45k tokens before turn 1!)
Skill (SKILL.md) = reusable instructions loaded on demand (name+description always visible; body loads only on match). vs CLAUDE.md = always loaded (fixed cost) · in-context = grows w/ session. API: beta headers code-execution-2025-08-25 + skills-2025-10-02 (runs in code-exec container). Subagents must be given skills explicitly.

8 · Images, PDFs & batch

  • Inline base64 – one-off image · URL – stable & public only · Files API – upload once, reuse file_id (beta; not on Bedrock/Vertex).
  • PDF → document block (same 3 sources; optional title/context).
  • Ambiguity in images: tell Claude how to handle overlap/occlusion.
Resize before ingest = 10-min fix. Calc on the LARGEST prod image.

Message Batches API

Cheaper per token, async. ✔ nightly 5,000 classify, eval runs. ✘ anything a user waits on. Looping sync calls in chunks ≠ batching → still rate-limited.

Match results via custom_id, never by position.

Cheat-sheet: the 8 takeaways

① wrong output → name the failure, add 1 technique (+ structured outputs) · ② thinking only where it changes the answer; return blocks unchanged · ③ stream end ≠ message_stop · ④ wrong tool = fix the description (add “don't use when…”) · ⑤ tool outputs burn context fastest → prune / compact / subagent · ⑥ workflow vs agent first; HITL before irreversible tools · ⑦ memory scope by session shape; Skills for on-demand instructions · ⑧ compute image tokens up front; Files API for reuse; Batches for offline.
